# Invoice data decision: synthetic set over the Kaggle CRM dataset

**Decided 2026-11-04.** The demo keeps the synthetic invoice set assumed in the build plan
(section 5.4, generated by WS1 with seed 42). A Kaggle "invoice dataset" was evaluated and
rejected. This page records why, so the question does not come up again in Phase 2.

## The candidate

[CRM Analytics (RFM-CLTV) on Kaggle](https://www.kaggle.com/code/ihsncnkz/crm-analytics-rfm-cltv)
is a *notebook* for customer analytics (recency, frequency, monetary value, customer lifetime
value). Notebooks of this class are built on the classic tabular **Online Retail** transaction
dataset: half a million UK e-commerce rows with columns such as `InvoiceNo`, `StockCode`,
`Description`, `Quantity`, `InvoiceDate`, `UnitPrice`, `CustomerID`, and `Country`.

## Why it loses to the assumed data

| Requirement of the demo | Synthetic set (plan) | Kaggle Online Retail rows |
|---|---|---|
| Document intake (PDFs and scans to parse/OCR) | Real PDFs (WeasyPrint) and damaged scans (Augraphy) | A CSV has no documents: nothing to parse, OCR, or box |
| Singapore tax invoice fields (IRAS/PINT SG) | GST number, 9% breakdown, UEN, PO, venue, bank account | UK retail transaction columns only |
| Engineered anomalies for R01–R12 | Hidden white text, swapped bank account, 8% GST, duplicate, statement, credit note, USD vendor, PO exceeded | No anomalies; every check would silently pass or error |
| Ground truth for evaluation and the gate | `InvoiceTruth` with expected coding and expected rules per document | No per-document truth, labels, or expected findings |
| Reproducible demos | Seed 42, byte-identical files, replay cache | A fixed downloaded snapshot (not reproducible by us) |
| Privacy and compliance posture | Fully synthetic, PDPA-safe | Real customer identifiers from a real UK retailer |

The pipeline's core stages — intake, on-page location, boxed review screen, hidden-text
detection, and the checks — all consume *documents*, not transaction rows. The candidate
dataset belongs to a different problem (marketing segmentation), so adopting it would mean
building a different product.

## What we would consider instead

If the demo ever wants real-world layout diversity, the plan already names the right
corpora: **FATURA** (10,000 invoice images, 50 templates, 24 labeled field types, CC BY 4.0),
**DocILE** (labeled business documents), and **invoice2data** (MIT sample PDFs). These are
documents with field labels — same shape as our intake — and any of them could enrich WS1's
templates later without changing the pipeline.

## Outcome

- **Kept:** the synthetic demo dataset from build plan section 5.4 (50 documents: 36
  "yesterday", 4 live, 10 benchmark), generated by WS1.
- **Rejected:** the Kaggle CRM RFM/CLTV notebook's underlying Online Retail dataset.
- **Unchanged:** `contracts-v1`, the golden fixtures, and WS1's brief.
